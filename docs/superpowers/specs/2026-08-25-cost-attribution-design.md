# 成本归因与预算策略设计说明 —— 单截面是 token 的正确设计，不是成本模型

**评审条目**：B2【P1】（`docs/design-review.md` §B2）
**规范章节**：`docs/architecture.md` §6.4（计量 UsageLedger）
**触及的待决事项**：README §四 待拍板 #3（项目与预算树的关系）—— 见 §9

---

## 1. 本项要解决的三件事

B2 的两条批评，加上核实现状时发现的一个已存在缺陷：

1. **成本模型只覆盖 token。** 连接器出向调用费、图/OLAP 查询算力、`ctx.jobs` 后台算力、复制日志存储增长、非 LLM 的 GPU 时间全部不在账上。
2. **预算树只有「单向耗尽」。** 没有借支、没有周期中调整、没有软限额预警。
3. **（新发现）PG 实现的预算扣减在最该生效的那一刻静默失效。** 详见 §2。

---

## 2. 先修缺陷：预算封顶在超限时静默关闭

`platform/dsh-plugins/metering/src/pg-meter.ts` 现状：

```sql
-- commit()
UPDATE budget_trees SET budget = budget - $2
 WHERE kind = $1 AND id = $3 AND budget >= $2
```

```ts
// reserve()
if (userRow.rows.length === 0 || userRow.rows[0]!.budget <= 0) → 拒
```

两个判断合起来产生一个**方向朝着「无限消费」的**失效：

| 步骤 | 状态 |
|---|---|
| 余额 500，本次消耗 600 tokens | `budget >= 600` 为假 → **0 行被更新，无报错** |
| 同一事务里 `usage_ledger` 插入 600 tokens | COMMIT 成功 |
| 下一次 `reserve` 读到 budget 仍是 500 | `500 > 0` → **放行** |

一旦「余额 < 单次调用量」，余额就**冻结在一个正数上，封顶永久失效**。台账照记，预算不动，没有任何错误浮出水面。而 `reserve` 只判 `> 0` 不判「够不够这一次」，所以剩 1 token 的用户可以发起任意大的调用。

**为什么它能活到现在**：`assertMeteringContract` 只对着 `MemoryMeteringSeam` 跑，而那个 stub 的 `commit` 是无条件减、允许负数——它满足契约，PG 实现不满足，两者都「通过」。这与制品注册表那处 parser differential 是同一个形状：**被验证的对象不是被依赖的对象**。契约测试只跑 stub 等于没跑。

**修法**：
- `commit` 的扣减必须无条件执行（允许负数），负数即透支状态，由 §5 的策略层解释。
- `reserve` 必须判「够不够这一次」，因此需要**预估量**入参。
- `assertMeteringContract` 必须能对着真 PG 跑（无库时 skip，但不得静默变成「只跑 stub」）。

> 「允许负数」不是放松封顶，恰恰是让封顶可判：余额永远非负时，「已透支多少」这个量根本不存在，也就无法区分「刚好用完」与「超了三倍」。

## 3. 成本类型是闭集，不是自由文本

现状 `costType: string`。自由文本维度撑不起 B2 的核心诉求——**「解释一次成本尖峰」**：没人能枚举一个自由文本列的取值，也就没法按类型下钻。

改为闭集，未知类型**拒绝入账**而不是记成 `unknown`：

| `cost_type` | 单位 | 发出方 | 说明 |
|---|---|---|---|
| `llm.tokens` | tokens | `ctx.llm` 截面（现有） | 唯一的 **token** 截面，B2 明确要求保留 |
| `connector.call` | 次 | 连接器网关（出向） | SaaS 按次计费 |
| `seam.query` | 扫描行数 / 字节 | 各 Seam Provider | 一条 LLM 生成的坏查询可能极其昂贵 |
| `job.compute` | 秒 | `ctx.jobs` | 后台算力 |
| `storage.bytes` | 字节·天 | 复制日志 / 对象存储 | 存储增长 |
| `inference.gpu` | 秒 | 非 LLM 推理 Provider | GPU 时间 |

> `seam.query` 的成本口径必须是 Provider 自报的**执行代价**（扫描行数/字节），不是墙钟耗时。墙钟含排队与邻居干扰，按它计费会让用户为别人的负载付钱。
>
> §5.3.4 把「LLM 生成的坏查询」当**安全**问题处理。本项把它同时当**成本**问题：同一条查询，安全侧管「能不能跑」，成本侧管「跑了记谁的账」。两侧不合并——安全拦截是布尔判定，成本记账是连续量。

**未捕获的成本必须被显式命名，不能静默缺席。** 这是本项的验收口径：账单解释不清是信誉问题，而信誉只死一次。因此 §10 保留一份「已知未计量」清单，而不是让读者以为账上就是全部。

## 4. 一个写入者，多个发出方

发出方跨语言（连接器网关是 Go，seam Provider 与 jobs 是 TS 插件），如果各自直连 PG 写 `usage_ledger`，schema 就有了 N 份副本，必然漂移——这与「幂等白名单两张表」是同一类错误。

**约束：`usage_ledger` 只有一个写入者。** 发出方产出**成本事件**，交给 sink：

```
连接器网关(Go) ─┐
seam Provider  ─┼─▶ CostEventSink ─▶ usage_ledger（唯一写入者）
ctx.jobs       ─┘
```

§6.4 已写明「计量事件走 RocketMQ `usage-events-<cost_type>`，不阻塞推理」（命名 2026-08-26 修正：原 `usage.event.*`，真实 broker 联调发现 topic 点号非法），那是目标形态。RocketMQ 尚未进部署拓扑（与 Nacos 同因，见 T1 落地状态的偏离记账），因此本期 sink 是**进程内直写 + 同一张表**，接口留成可替换的那一层。这是排期上的临时顶替，不是对异步削峰的否定。

## 5. 预算三态：预算内 / 透支中 / 硬停

B2 说「不补这些，配额首次上线就会被业务方要求回滚」。更准确的失效路径是：**只有硬停时，运维会把预算设成无穷大**，于是预算系统在名义上存在、实际上不存在。所以软限额不是锦上添花，它是这个功能能不上线就被绕过的分界线。

| 状态 | 条件 | 行为 |
|---|---|---|
| `within` | 已用 < 软限额 | 放行 |
| `soft` | 软限额 ≤ 已用 < 预算 | 放行 + **结构化预警**（同一周期同一树只警一次） |
| `overdraft` | 预算 ≤ 已用 < 预算 + 透支额度 | 放行 + 预警升级；透支量需事后结算 |
| `hard` | 已用 ≥ 预算 + 透支额度 | 拒绝 |

- **透支额度默认 0** —— 即默认行为与今天一致（硬停在预算处）。开启透支是显式决定，不是默认继承。
- **周期中调整**：`setBudget` 必须能提额也能降额，且**降额不得追溯**——降到低于已用时状态立刻变 `overdraft`/`hard`，但不回收已发生的消费。追溯回收等于把过去的合法调用变成违规。
- **预警去重**：同 (周期, 树, 状态) 只发一次。这与闸 C 的告警去重同理——刷一百条相同预警等于埋掉信号。

> 并行双树下状态取**两棵树里更严的那个**：user 在 `soft`、project 在 `hard` 时结果是 `hard`。理由与 N3 的「任一超限即拒」一致。

## 6. 归因链必须能反查

`usage_ledger` 已有 user/dept/role/project/agent/component/feature/session_ref。B2 要求「携带同一 trace context」，因此新增：

- `trace_id`：把一次 request 内跨语言、跨成本类型的多行串成一条因果链。没有它，「这次尖峰是哪个请求引起的」只能靠时间戳猜。
- `emitter`：发出方标识（哪个网关/Provider/job）。出账争议时要能定位到具体组件而不只是组件类别。
- `qty` + `unit`：`tokens` 列只能装 token。成本类型闭集里有次/行/秒/字节，塞进同一个 `tokens` 列会让口径不可读。`tokens` 保留（不破坏现有查询），新增 `qty`/`unit` 承载非 token 量。

---

## 7. 不做的事

- **不做费率表与出账**。`cost_usd` 保留为 Provider 自报，费率管理、汇率、折扣是计费系统的事，塞进 seam 会让它变成第二个真相源。
- **不做派生聚合引擎**。本项只保证明细完整且可下钻；日粒度聚合由 §6.4 的查询面在台账上直接分组完成（原计划的 Doris 看板 cube 已于 2026-09-14 按决策移除）。
- **不做限流**。Redis 令牌桶是另一件事：限流管速率，预算管总量，混在一起会让「超速」与「超额」用同一个错误码返回。
- **不追溯补齐历史成本**。新维度对历史行为空，不回填假数据。

---

## 8. 与第一铁律的关系

全部改动在 `platform/`：`shared/seam-contracts/metering.ts`（契约）、`dsh-plugins/metering/`（PG 实现 + 插件）。发出方接入点用 dsh 原生事件瀑布与 seam Provider 注册，零 dsh 源码改动。

## 9. 触及一项待决事项 —— 必须显式说明

README §四 待拍板 #3：「项目是**归因维度**还是**并行预算树**？」**仍未拍板**。

但 `pg-meter.ts` 已经实现了并行双树（user + project 各一棵，任一超限即拒），即代码已经站在「并行预算树」这一侧。本项在这个既成事实上继续（三态与透支同时作用于两棵树），因为改回「纯归因维度」是删功能而不是加功能，成本更低、可逆。

**这不构成拍板。** 若最终决定项目只作归因维度，需要删掉 `budget_trees` 里 `kind='project'` 的那一半与相应状态合成逻辑；本项的三态模型对单树同样成立，不会成为阻碍。

## 10. 验收判据

| # | 判据 |
|---|---|
| 1 | 余额 500、消耗 600 时余额变 −100（**不是停在 500**），且状态判为 `overdraft`/`hard` |
| 2 | `reserve` 判「够不够这一次」：余额 1、预估 100 → 拒；余额 1 未指定预估 → 仍按剩余量判 |
| 3 | `assertMeteringContract` 对**真 PG** 跑通；无库时 skip 且 skip 可见（不静默降级为只跑 stub） |
| 4 | 未知 `cost_type` 入账被拒绝，错误信息列出合法取值 |
| 5 | 六类 `cost_type` 各能落一行，且 `qty`/`unit`/`trace_id`/`emitter` 完整 |
| 6 | 同一 `trace_id` 能把跨类型的多行取回为一条因果链 |
| 7 | 四态转移正确；透支额度默认 0（行为与今天一致）；降额不追溯回收 |
| 8 | 预警同 (周期, 树, 状态) 只发一次，且字段结构化可断言 |
| 9 | 已知未计量成本在文档里被显式列名，不静默缺席 |

**已知未计量（判据 9 的清单）**：跨节点网络流量费、PG/Doris 存储的实际计费口径（本项只记字节·天，不含 IOPS）、控制面自身算力（Scheduler/registry 的开销不摊进业务账）、人工审批的人力成本。列名的目的是让读账单的人知道边界在哪。
