# 空间协作指挥台设计

日期：2026-09-17
状态：设计已评审通过（图结构、智能体来源、绑定方式三项经用户确认），实现进行中
范围：新增一个 surface，把「注册节点员工 + 他们的上下游 + 服务于他们的智能体」做成空间视图

---

## 0. 先记两次走错的路（它们比结论更有用）

**第一版：把 mockup 当规格照搬。** 做成「读 governance 委派表、按 `parent_task_id` 画层级」，
还往测试里塞了写死的示例数据。错在两点：① mockup 是**参考**不是规格；② 图上的 Agent 是
dsh 的真实多智能体，不是从委派行推出来的标签。

**第二版：只在 governance 里找依赖。** 由此断言「依赖没有数据源，不做」。**这个结论是错的**
——`TeamTask.dependencies[]` 就是真依赖边，只是它在 agent-teams 里，不在 governance 里。
**教训与 E7b 同族**：把「我在这个模块里没搜到」记成「这个数据不存在」，差别只在于检索范围。

## 1. 图是什么（经用户确认）

- **节点 = 注册节点的员工**：`/v1/users` 拿人，`/v1/desktop-nodes` 拿他名下的注册节点与在线状态。
  节点状态是「这台机器还能不能接活」的问题，只有放在人身上才读得通。
- **边 = 员工之间的上下游**：由委派链折出来——父任务的承担者在上游，子任务的承担者在它下游。
- **智能体挂在它服务的员工下面**：凭 `TeamMember.ownerUserId` 这个**显式**字段。
  没有绑定就进「未绑定」区，**不猜、不丢**。

## 2. 为什么必须有显式绑定

员工与智能体之间**原本没有任何共同的键**：`TeamMember` 只有 `name`/`role`/`provider`/`model`/`status`，
而团队是由**模型通过工具**创建的（`agent_teams_create` / `agent_teams_add_member`），平台代码不参与，
所以没有任何地方知道「这名成员为谁工作」。

名字不是键（会重名、会改）；会话 id 也不通用（单机是临时子代理，集群在别的节点上）。
所以本包给 `TeamMember` 加了 `ownerUserId?: string`，并按**四段一起改**：

| 段 | 落点 |
|---|---|
| 声明 | `model.ts` 的 `TeamMember.ownerUserId?` |
| 写入 | `service.ts` 的 `addMember`（空白串归一成「未提供」） |
| 持久化 | 整体交给 KV，自动带上 |
| **重载** | `store.ts` 的逐字段解析——**漏了这段，字段会被写进介质却在读回时无声丢掉** |

第四段是这套东西里唯一容易漏的：症状是「重启后智能体全变成未绑定」，而写入侧看起来完全正常。
规则由一条 round-trip 用例钉住，并做过变异验证（摘掉那段解析 → 用例转红，`ownerUserId` 读回为
`undefined`）。

## 3. 数据流

```
客户端  →  五个面各取各的，拼接在纯函数里
          /lumo/api/users                → 员工是谁
          /lumo/api/desktop-nodes        → 名下注册节点与在线状态
          /lumo/api/delegations          → 任务在谁手里（上下游由此折出）
          /lumo/api/collaboration/teams  → dsh 团队名册（新路由 ← ctx.agentTeams）
          /lumo/api/overview             → Scheduler /v1/nodes → Nacos 健康执行实例
```

**五个读面各自降级**（`Promise.allSettled` + 逐面说明）：任何一个拿不到，只在图上少一块并写明
原因。用 `all` 的话缺一面整张图就空了——而「某个服务没装」与「组织里没有协作」在读图的人眼里
是两回事。

**新增的路由只有一条**（`/lumo/api/collaboration/teams`）。员工、注册节点、委派都已各有各的面，
拼接是纯函数、放在客户端可单测；在服务端造聚合端点只会多一处「两边字段一起改」的地方。

`ctx.agentTeams` 用**机会式**取法（不进 `ctx.inject` 列表）：inject 会等列出的服务全部就绪才注册
路由，把它加进去等于「没装 agent-teams 的形态整个 `/lumo/api` 都不工作」。取不到时该路由回
**503 并说明缺席**——空列表读起来是「没有团队」，那是一个结论，不是缺席。

## 4. 可测内核（`collaboration-layout.ts`，纯函数）

1. **`employeeFlowEdges(tasks, employeeIds)`** — 委派链 → 员工边。四条取舍：自环丢掉（同一个人
   既是父又是子）、两端都要有承担者、承担者必须是本页的员工、**同向去重**（线的数量不该取决于
   任务数，否则会读出不存在的「联系很密」）。一来一回是两条**不同**的边，不合并。
2. **`employeeState(employee, tasks)`** — 优先级按「看的人能做什么」排：
   `awaiting-review`（看图的这个人的动作被卡住，压过一切）→ `offline`（名下节点全掉线，压过
   blocked/executing：机器接不了活这件事最该喊出来）→ `blocked` → `executing` → `delivered`
   → `queued` → `unknown`。**词表外一律 `unknown`**；没有任务的员工是 `unknown`，不是「已完成」。
3. **`bindAgents(agents, employees)`** — 只认 `ownerUserId`。绑定指向不存在的员工时同样进
   「未绑定」，**不是挂到一个幽灵员工上**——两种错法的可见度差很多：前者是图上一块显眼的区域，
   后者是一根指向空气的线。
4. **`layoutCollaboration(...)`** — 纵深 = 上下游深度（最长路径松弛，带环终止上界），同深度按
   **id 排序后居中**。按 id 而不是到达顺序：同一批数据换个顺序请求，位置必须不变，
   否则「右上角那个」不再是一句有效的指代。

## 5. 交互

| 交互 | 实现 |
|---|---|
| 空间缩放 | 一个缩放因子 → `scale`；纯数值，可断言 |
| 节点聚焦 | 选中员工 → 右侧面板显示其注册节点 / 名下智能体 / 上下游深度 |
| 返回对话 | 顶部固定主按钮关闭协作 surface，不能依赖浏览器后退 |
| 重新读取 | 五个面并发重取，各自降级 |
| 自然语言下达目标 | 底部的目标输入把文字**交给「项目」那一个委派流程**，自己不创建。「项目」里那条链已经完整（候选人排序预览、自动/手动分发、调度约束）；在这里重写一份会造出两个必须就创建体保持一致的调用点，而它们迟早分叉——症状是「同一句话在两个入口分发结果不同」。交接走模块级变量且**取用即清空**，所以手动进「项目」不会被上一次的目标污染 |

**刻意不做**：自由旋转、拖拽改布局（会让「同一个员工永远在同一个位置」失效，而那条性质是这张图
能当运维视图用的前提）。

## 6. 不做

- **不做依赖边之外的推断关系**：图上每条边都能指回一条委派事实。
- **不按名字猜绑定**（§2）。
- **不改 governance**：员工、节点、委派三个面都直接用现成的。
- **不做 3D 旋转/环视**（§5）。

**渲染证据的边界要说清楚**：它证明「规则被画成了 DOM」，**不证明规则本身对**。实测验证过这个
分工——把 `offline` 提到 `awaiting-review` 之前，`collaboration-layout.spec.ts` 转红，而这两条
渲染用例仍然全绿（夹具刻意把两种状态放在不同的人身上，好让一张图上同时看到它们）。
**两层不是替代关系**，缺任何一层都会漏掉一类错。

## 8. 一个必须写下来的坑：`pnpm run typecheck` **不覆盖客户端**

本包的客户端代码（`src/client/**`，含近 3000 行的 `index.tsx`）**在 CI 上从来没有任何类型检查**：

- 根 `platform/tsconfig.json` 显式 `exclude: ["dsh-plugins/*/src/client/**"]`——因为浏览器侧要 DOM lib 与
  jsx，而根工程是 Node 侧配置。这个排除本身是对的。
- 但**没有任何地方补上被排除的那一半**：`pnpm run typecheck`（CI 跑的就是它）只编根工程。
- 客户端的检查要用 `dsh-plugins/lumo-ui/tsconfig.json`（`include: ["src"]`，extends 上游的
  `tsconfig.base.client.json`），本包为此加了 `pnpm run typecheck:client`。

**这个坑是本包自己踩出来的**：我先按老习惯用 `tsc -b --noEmit` 验证，一路 PASS；换到
`typecheck:client` 才暴露出 2 个真实的类型错误（`exactOptionalPropertyTypes` 下把
`string | undefined` 赋给可选属性）。更刺眼的是，**注入一个确定的语法错误后，两种
`tsc -b` 都照样报 exit 0**——因为它压根没编那个文件。

**它为什么没被接进 CI**：客户端检查需要上游 `lib/types`，而 `tsc -b tsconfig.client.json`
在**上游 master 自己的客户端代码上就失败**（`ui-settings-models`、`test-support/remote-mock`
的测试文件）。第一铁律不允许为此改 dsh，所以这一步只能先作为本地工具存在。
**别把它当成「已经覆盖了」**——它现在没有被任何自动化跑。
