# 集群本地放置降级设计

日期：2026-09-17
状态：设计已评审通过（范围经用户确认：只做这一条，不拆进程），待实现
范围：`architecture.md:721` 点名的那件事——「集群本地放置降级随集群 Scheduler 落地」

---

## 0. 它解决什么

`architecture.md:703` 要求「一个**全局调度**是唯一放置决策点，各**集群 Scheduler** 仅受理工作」，
`:721` 紧接着写下降级曲线：「无 leader 时放置请求**快速失败**（503 no-leader，绝不挂起）；
**集群本地放置降级随集群 Scheduler 落地**」。

今天只有前半句实现了：`internal/server/server.go:181-185` 在没有租约时对**所有**放置返回 503。
于是**全局调度一挂，每个集群连自己集群内的活都放不下去**——而「本集群的任务落在本集群的节点上」
本来不需要任何跨集群信息。

**范围修正（2026-09-17 晚，实现后复核）**：本节原本写着「不拆进程、不动部署形态」。实现完发现
**那样写是错的**——降级需要「本实例属于哪个集群」这个身份，而唯一服务两个集群的全局实例既没有、
也不该有它。所以不动部署形态的结果是：**代码、测试、指标、告警全都齐全，而那条路径在任何拓扑里
都走不到**——正是本仓库记过多次的「门禁齐全而闸门从未打开」。

因此最终范围是**只动必要的部署面**：在 `compose.cluster.yml` 里加两个**每集群一份**的 scheduler
实例（`scheduler-cluster-a` / `scheduler-cluster-b`，带 `LUMO_SCHEDULER_CLUSTER_ID`），全局那对
主备原样保留。这不是「拆进程」意义上的完全分层（没有独立二进制、没有独立代码路径），但它让
两个角色的**实例**真的存在，于是降级可达。

同步的接线面（实测出来的，不是数出来的）：`compose.cluster.yml`、`preflight-deployment.sh` 的
期望服务集、`prometheus.yml` 的抓取目标、`probes-cluster-verify.sh` 写死的派生目标数，
以及 `cluster-registry-verify.sh` 的**三条反例**——最后这一处值得单独说：那两个实例加进去之后，
「移除承载节点的上报地址」与「清空所有 LUMO_SCHEDULER_URL」**不再构成缺陷**（该集群仍有本地实例
在上报），反例于是开始报「缺陷没有被抓住」。反例要跟着不变式一起长，否则它会在门禁仍然有效时
持续喊狼来了。

## 1. 为什么不能简单地「没 leader 就放行」

`lease` 不只是「我是 leader」的标记，它是**受围栏保护的写凭据**：`PlaceTask` 在写事务里调
`checkFencing`（`store.go:341-358`），比对持有者与 token。直接放行等于取消围栏——而本仓库
在 D3 那一轮刚在同一个位置挖出过「`replicaCount: 2` 静默造出两个互相没有 fencing 的 leader」。
**无 leader 降级必须是「换一把更小的锁」，不是「把锁拿掉」。**

## 2. 设计：集群作用域的第二把租约

新增一张**独立的**租约表，而不是给现有表加行：

```sql
CREATE TABLE IF NOT EXISTS scheduler_cluster_lease (
  cluster_id    TEXT PRIMARY KEY,
  holder        TEXT    NOT NULL,
  fencing_token BIGINT  NOT NULL,
  expires_at    BIGINT  NOT NULL
);
```

三个理由，每条都对应一个具体的坏结果：

- **独立表而不是复用 `scheduler_leader_lease` 加一个 id 维度**：那张表的 `id` 是整数且写死为 `1`
  （`store.go:292` 的 `VALUES (1, …)`），改类型要在**已上线**的表上做迁移；而两把锁的**语义本来就
  不同**（一个是「跨集群唯一决策者」，一个是「本集群唯一决策者」），放进一张表只会让
  「哪些行算 leader」变成一个需要解释的问题。
- **`cluster_id` 做主键**：一个集群一把锁，天然表达「每集群至多一个本地决策者」。
- **不建全局唯一约束**：不同集群的本地锁互不相干，这是它们存在的意义。

`domain.Lease` 增加一个字段来指明它属于哪把锁：

```go
type Lease struct {
    Holder       string
    FencingToken int64
    ExpiresAt    int64
    // Scope 空 = 全局租约（scheduler_leader_lease）；
    // 非空 = 该集群的本地租约（scheduler_cluster_lease）。checkFencing 按它选表。
    Scope string
}
```

`checkFencing` 从「`WHERE id = 1`」改成「按 `lease.Scope` 选表」——**这是本设计唯一改动围栏的地方**，
也必须在同一次改动里由用例钉住两个方向：全局租约不能通过集群表的校验，反之亦然。

## 3. 放置路径的判据

```
有全局租约            → 走今天那条路（不降级，行为完全不变）
无全局租约 且 未设 -cluster-id   → 503 no-leader（今天的行为，保持不变）
无全局租约 且 设了 -cluster-id   → 仅当「请求的 cluster_id == 本实例的 cluster-id」
                                  且「本实例持有该集群的本地租约」时放行，并打降级标记
                                  否则 503 no-leader
```

**没有集群身份就不降级**，这一点是刻意的：一个不知道自己是哪个集群的实例，无从判断「本地」
是什么。它今天只能 503，改后仍然只能 503——**不猜**。

**跨集群请求在降级期间一律 503**：那是真正的「全局」决策，而全局决策者不在。用本地锁去批准
跨集群放置会造出比 503 坏得多的东西（两个集群各自以为自己是决策者）。

## 4. 观测

降级不是静默的：

- 指标：`lumo_scheduler_degraded_placements_total{cluster_id}`——计数降级期间成功放行的次数。
  只加 gauge 不加这个计数，就没人知道系统正在降级运行。
- 启动/切换日志：进入与退出降级各记一次（不只是每秒重复）。
- 放置响应带标记（`degraded: true`），让调用方能区分「正常放置」与「降级放置」。

## 5. 测试

| 层 | 内容 |
|---|---|
| **围栏（最重要）** | ① 全局租约通过 `checkFencing`，② 集群租约通过 `checkFencing`，③ **全局租约不能通过集群表的校验**（交叉反例——只测「好输入能过」的门禁，在选表被写错时仍会全绿） |
| 租约获取 | ④ 同一集群两个持有者：第二个拿不到（`ErrNotAcquired`）；⑤ 不同集群互不阻塞；⑥ 易主时 token +1、续租不换 token |
| 放置准入 | ⑦ 有全局租约 → 不降级；⑧ 无全局租约 + 未设 cluster-id → 503；⑨ 无全局租约 + 本集群请求 + 持有本地租约 → 放行且标记降级；⑩ 无全局租约 + **跨集群**请求 → 503（即使持有本地租约） |
| 观测 | ⑪ 降级计数只在降级路径增长 |

## 5.1 端到端证据（两个真进程 + 真 PG）

三个真二进制实例，同一个库、同一个请求体，只有配置不同：

| 实例 | 配置 | 请求 `cluster_id` | 响应 |
|---|---|---|---|
| A | 全局（无集群身份），**持有全局租约** | cluster-a | `worker-directory-unavailable` —— 越过闸门（正常路径） |
| B | `LUMO_SCHEDULER_CLUSTER_ID=cluster-a`，**拿不到全局租约** | cluster-a | `worker-directory-unavailable` —— **越过闸门（降级路径）** |
| B | 同上 | cluster-b | `no-leader` —— 跨集群仍被拒 |
| C | 无集群身份，**拿不到全局租约** | cluster-a | `no-leader` —— **这就是改动前对所有请求的行为** |

**B 与 C 打在同一个请求上结果不同，是这次改动的定义**：有集群身份 + 持有本地租约 → 本集群可放行；
没有身份 → 与从前完全一样。

两处不在这张表里的东西，说明白免得被读成「已验完」：① 响应停在 `worker-directory-unavailable`
而不是 201，是因为本机没起 governance（那道闸门与本次改动无关，且在降级路径**之后**）；
② `degraded: true` 标记与降级计数没有在上面这几行里被断言——它们由 `internal/server` 的单测钉住，
而这里证的是**闸门开不开**。

启动日志同时证明了两件事：`集群本地决策权变更（降级路径） leader=true cluster_id=cluster-a`
（拿到了本地锁），以及 `集群自报已启用`（自报归到了本地实例）。

## 6. 不做

- **不做独立二进制/独立代码路径的分层**：两个角色由**同一份代码 + 不同配置**承担（`-cluster-id`）。
  与「不变更部署形态」的区别见 §0 的范围修正——加了两个实例，但没有第二套服务实现。
- **不动 Helm chart**：`scheduler-cluster-a/b` 只进了 compose。chart 要表达「每个集群一份」需要
  先回答「chart 怎么知道有哪些集群」（一个 `scheduler.clusters` 列表？还是从 dshNode 的取值派生？），
  那是独立决定。**这一条必须写在显眼处**，否则「compose 有、chart 没有」会在某次真机验收上
  以「降级没生效」的形式出现，而原因在两份拓扑不一致。
- **不撤 dsh-node 侧的上报方**：注册表本就接受多个上报方，而「先加替代者、验证它确实在报，
  再撤旧路径」比一次改动两头都动安全。本轮已证 `scheduler-cluster-a` 确实在上报（启动日志
  「集群自报已启用」+ 静态门禁把它列为上报方），撤旧路径留作独立一步。
- **不改 reconcile 的 503**（`server.go:527-531`）：对账是带围栏的写路径，与放置的准入判据不是
  同一件事，混在一起改会让两边的语义都变模糊。
- **不做跨集群的降级放置**（§3 末句）。
- **不动 `scheduler_tasks` 的状态机**：降级只影响「谁有资格写」，不新增任务状态。
