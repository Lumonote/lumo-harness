## 1. Provisioner：声明式 reconcile（§6.5 的可执行化）

### 1.1 职责分离

| 进程 | 机关 | 职责 |
|---|---|---|
| `control-plane/provisioner`（Go） | 控制面 | 期望态编辑（agent manifest → 制品闭包 plan）、签发**安装指令**、节点原子变更记录（rollouts）、状态聚合 |
| `@lumo/provisioner`（dsh 插件） | 数据面（每节点） | 拉取安装指令 → **复验**（digest + 验签 + 重解析，§2.1 注册表说明）→ Fetch 字节 → 解包 → 热装载/卸载（Cordis 插件图）→ 心跳上报实际态 |

一个节点的安装器是**装配层的一部分而非独立服务**：装载插件图本来就是 Cordis 的领域，独立 Go 进程装不进 dsh 的 `isolate` realm——这正是「业务 capability 插件形状」的分界（§3.1）里 provisioner 消费者用插件的理由；控制面侧（期望态/计划/状态）是后台服务，不做进插件。

### 1.2 状态机（reconcile 的单元）

```text
pending → installing → ready
                     ↘ failed(msg)
   心跳差异检测: 实际态 ≠ 期望态 → 重新 plan → installing
```

- **期望态** = agent manifest 声明的 `deps`（制品名 + 版本约束），存 registry PG（版本约束不解析成固定版本——「期望态」就是约束本身，闭包解析交给每次 plan）；
- **实际态** = 节点 heartbeat 上报的 `{installed: (name, version, digest)}[]`；
- **差异即计划**：reconcile 循环不做增量复杂性管理——每次差异都是一次完整的 `plan → resolve → 验签 → 装载→ 上报`；
- **幂等装载**：同 digest 重装载 = no-op（`ctx.plugin()` 幂等重复挂载的 Cordis 规则为约束——重复装载失败即 reconcile 失败并面向上层报出，永不静默换版本）。

### 1.3 装载的正确性边界

- **安装端只信原始字节**（registry §2 的核心断言延续）：计划里的 `(name, digest)` 只是**索引**；安装器按 digest 取字节 → 验签 → **重新解析** → 从解析结果读 `requires`/`deps`/`scopes` 做形态校验与装载判断。PG 元数据任何一处不得作为安装端执法输入。
- **形态校验双保险**：`plan` 阶段已拒（registry §6）；装载是 `plan` 之后的第二道闸——同样校验 `requires`，因为计划可能过期（节点形态在计划后变化）。
- **热装载的回滚由插件图保证**：装载失败时 Cordis 的 `isolate`/plugin 卸载语义是回滚动作的来源；失败即上报 `failed(reason)`，**不保留半装载状态**——这要求每个插件装载动作无副作用地挂在 `isolate` 上（不得在 `apply()` 里二次副作用）。

### 1.4 MCP server 下载（registry §1 延后项在此收账）

MCP 属第五类制品？不——MCP server 是**连接器/组件的一个子形态**（B1 判定树：外部系统契约端 = Connector）。因此 MCP 下载**不另设制品类型**：MCP server 连接器 manifest 走同一闭包解析，provisioner 下载其 bundle（含可执行文件）并按连接器契约装载。**proc 边界**：MCP server 以 `ctx.subprocess` spawn、`ctx.sandbox` 约束——远程形态判 `never`（分级表）在此保持一致，MCP server 的远程化走 E2B 式专用路径而非 SeamProxy。

### 1.5 不做的（下下批）

- 运行时自动回滚（deploy 失败自动回退上一版本——先人工裁决，机制留给「灰度审核」）
- 跨集群制品同步（联邦复制，归 N6 数据驻留）
- 节点磁盘上的制品缓存策略（MinIO 拉取走 `ctx.datastore.object`，缓存节点本地内容寻址、TTL 与 GC 随对象存储生命周期管理）

## 2. OPA scope 评估：哪些决策是「策略」，哪些是「机制」

OPA 的适用判据：**三条件**——① 决策需要**可变规则**（策略会变，不是一张写死的表）；② 决策在**信任边界**上（输入含跨主体凭据/声明）；③ 决策失败的代价是可解释的拒绝（fail closed 且报得出因）。三个条件全满足才进 OPA；缺任何一个即是机制，放 OPA 会把机制**变成可改的规则**——预算上限今天被改一个 Rego 文件就失效，这类「策略化」就是不可追责的失效入口。

### 2.1 归 OPA 的决策（三条件全满足）

| 决策点 | 输入 | 裁决 | 理由 |
|---|---|---|---|
| 工具可执行（pre-execute） | provenance 的 turn 污点 + 工具副作用级 + 角色 | 放行/收窄/HITL（§18.2 职责分离） | 可变规则、信任边界、可解释拒绝 |
| 连接器出向调用 | realm + scope + egress 目标 + 角色 | 放行/拒绝/配额提醒 | 同上；与四道闸是「决策+执行」的先后关系 |
| registry 发布授权 | publisher 身份 + 申请 scope + 信任树上限 | 放行/拒绝并报超限项 | 可变（新角色/新审计要求）、信任边界 |
| 预算调整（setBudget/adjustBudget） | 操作者 + 预算关系（项目与预算树——**依附待拍板 3**） | 放行/转 HITL | 可变、信任边界（运维职权） |

### 2.2 不进 OPA 的（机制，改成规则反而不利）

| 决策点 | 当前机制 | 不放 OPA 的理由 |
|---|---|---|
| 预算三态判 `reserve` | `budgetState` 纯策略 + PG 执法 | 数值判定，规则不变；与 OPA 同构反而把«已超预算»变成可配置，且每次 reserve 决策要过网络（性能） |
| 限流额度 | Redis 令牌桶（§6.4） | 数据面高频、规则固定 |
| seam 远程化准入 | `remotability.ts` 分级表**代码闸** | 表就是真相源（注释已写），逐例定级有人审；放 OPA = 可运行时改「哪条 seam 能过网」，改错即越权 |
| 出平台写转 HITL | `control` 审批通道（§10.3） | 是执行器不是裁决器（判据已在 2.1 第一行给出） |
| 调度放置策略 | Scheduler（§6.2） | **待定**：跨集群放置与节能策略想进 OPA，但输入是延迟/资源水位这种数值，Rego 表达力强而性能敏感——**列为待观察项**（SLO §21.3 容量基线诞生后再评估） |
| 周期结转/预算重配 | 运维命令 + `setBudget` | 单向、低频、人直接操作，无「策略」可言 |

### 2.3 registry 侧的 OPA 关系（收「OPA scope 评估」的义务）

registry 的 publisher scope 上限校验（发布授权）**进 2.1 的第三行**；第 7 条验收判据（超上限拒）当前在 trust store 完成——本设计让**规则三条件检验先行**：信任树上限是静态声明（PG trust store，随密钥治理 §3 一起），OPA 负责其中的「角色×申请 scope」裁决。两处是「静态上限（data）+ 动态裁决（OPA）」的补全关系，不是替代关系。

## 3. 密钥轮换与吊销（registry §9「私钥保管与轮换」的收账）

### 3.1 现状的漏洞（为什么这条不能拖）

registry 用 ed25519：publisher 私钥签名制品字节，安装端用 trust store 公钥验签。**泄漏一旦发生**：私钥仍有效 → 攻击者可发布「签名合法」的任意制品（§9 的「签名不证明良性」在此叠加——**良性泄漏不是攻击,是管理事故**）。租约：没有轮换与吊销列表,泄漏发现后唯一的响应是「全员重装系统」——这不是处置,是事故。

### 3.2 密钥生命周期

```text
签发: 每安全身份一钥(人/机器人 CI 各一), 私钥只入 Vault(KV + transit 加密), 绝不进仓库/镜像/日志
发布: 制品签名 = ed25519(nonce || sha256(bytes));  公钥 + 可授予 scope 上限 → PG trust store
轮换: 双钥窗口——旧钥仍验(宽限期 30d, 可配置), 新钥即可签发;
      窗口内: 旧钥签的存量制品仍然可安装(旧公钥在 trust store 内)
吊销: 旧钥移入 revocation list(发布问题者) → 立即生效: 凡旧钥签发的制品, 解析/装载时一律拒绝
      —— 字节未变也拒绝: 信任的是「这个主体发的东西」, 不是「这串字节」, 信任撤回与字节无关
```

### 3.3 安装端处理（吊销的分布）

- 吊销列表是**随 resolve 一起取回**的（安装端**禁止仅凭本地缓存列表验签**——这是「吊销列表未同步」被误认为「签名合法」的窗口）；每个 plan 响应附 `revocations[]`，验签时先查列表。
- **已安装的制品不因吊销自动卸载**（信任撤回不等同于删除；删除是处置动作，由 realm 管理员在控制面发起——避免「升级事件导火索变成数据损坏事故」）。
- 泄漏响应流程：吊销 → （控制面审计：该身份签过哪些制品）→ 重发（新钥、新版本）→ 灰度 → 定期清理失效版本（依赖图完整引用校验后）。**全程挂 §19.3 的注入清单**：吊销列表注入测试属混沌注入新行。

### 3.4 与 Vault 的边界

- 私钥保管、TTL、审计访问 → Vault（§6.3：参数只存指纹、值只在 Vault）；
- 撤销/吊销记录 → PG trust store（随制品元数据，清单级一致）；
- **两处不一致以吊销列表为准并报错**（同 registry §2 的「以 MinIO 为准报错」哲学——不一致是事件，不是漂移）。

### 3.5 验收判据

1. 新钥签发、旧钥宽限期、宽限期满吊销三段各自可验证——**吊销后旧公钥验签失败且报出吊销日期/原因**
2. 发布同 digest 幂等；同版本不同 digest 拒（沿用 registry）
3. OPA 决策点表(2.1)每行有单测(可用 Rego 单测; 未接入前以 trust store 子集检查测试覆盖)
4. provisioner: 上传计划 → 节点验签重解析 → 装载 → 心跳实际态；计划过期（形态变化）导致失败时第二道闸检出
5. 吊销注入测试: 计划下发后吊销 → 安装端拒绝, 已安装的保持
