## 0. 决策背景

平台已经有 11 个 dsh 插件和 3 个 Go 服务在跑，**但没有任何分发通道**：插件靠装配层手工 `ctx.plugin()` 挂载，制品没有版本、没有签名、没有依赖声明。§16.2 的 P1「组件化 + 技能分发」整档跳过了，却已经在做 P2 的跨节点能力。这是当前最靠前的结构性阻塞——每多建一个插件，回头改装配方式的成本就多一份。

T1 已经给出职责三分的结论（二进制→MinIO / 元数据+签名+依赖图→PG / 灰度规则→Nacos Config），本设计把它落成代码，并回答 T1 没有回答的那个问题：**校验在哪一侧、信谁的字节**。

B1 与本项同期做，因为 manifest schema 必须先知道「五类各自是什么」才写得出来——判定树不是文档洁癖，是 schema 的前置。

## 1. 范围

**在范围内：**

- **五类制品 manifest schema**（`shared/manifests`）：Component / Skill / Agent / Connector / Flow
- **registry 服务三个动作**：`publish`（发布）、`resolve`（解析依赖闭包）、`plan`（生成安装计划）
- **内容寻址存储**：`ObjectStore` 接口 + MinIO 实现 + 本地文件实现（供 Local-lite 与测试）
- **签名与信任链**：ed25519；publisher 公钥与其可授予 scope 上限存 PG trust store
- **依赖闭包解析**：环检测、版本冲突裁决、形态校验（§13.2.3）
- **B1 判定树**写进 §4.3；**§6.1 措辞**按 T1 修订

**不在范围（明确留给后续项）：**

- **provisioner**：真正把 bundle 装进 dsh 节点、热加载、reconcile 自愈（§6.5）。本项只产出**安装计划**，不执行安装。切在这里是因为计划生成是纯函数、可完整测试，而安装是与 dsh 运行时耦合的副作用
- **Nacos 真实接入**：本项用 `ReleaseChannel` 接口 + PG 实现（`rollouts` 表）。与 Scheduler 用 PG 租约而非 Nacos 是同一个偏离，理由相同（见 §6），**同样必须记录在案而不是默默做掉**
- **OPA scope 评估**：策略服务未建。本项用 trust store 里的 publisher scope 上限做**子集检查**顶上，接口留给 OPA
- **MCP server 下载**：属 provisioner
- **制品市场 / 浏览 UI**：属产品面

## 2. 核心设计：PG 是索引，不是真相源

T1 写的是「签名与信任链**在 PG 校验**」。这一句需要修正，它是本设计唯一一处与评审意见的实质分歧。

制品字节存 MinIO（sha256 内容寻址），manifest 解析后的元数据存 PG 供查询与依赖解析。如果安装端拿 **PG 里的元数据**做执法判断（这个制品要什么 scope、要什么部署形态、依赖谁），那么 **registry 的数据库就成了信任根**：一次 SQL 注入、一次运维误操作、一个越权的内部账号，就能把 `scopes: [kb:query]` 改成 `scopes: [data:write:*]`，而 MinIO 里那份被签名覆盖的原始字节纹丝未动，签名照样验得过——因为签名验的是字节，执法看的是数据库，两者从来没有对上。

这是 parser differential 攻击的标准形状：**签名覆盖的对象与执法依据的对象不是同一个对象。**

因此本设计的硬约束：

> **安装端只信 MinIO 里那串被签名覆盖的原始字节。** 收到安装计划后，按 digest 取字节 → 验签 → **重新解析** → 从解析结果读 scope / requires / deps 做执法。PG 元数据只用于查询、列表、依赖图遍历，**任何一处执法判断都不得以它为输入**。

两个推论：

1. **不做规范化重序列化再签名**。签的就是上传时的原始字节，逐字节。规范化（JSON 键排序、Unicode 归一）会引入「两个实现算出不同规范形式」的失配，而失配的后果不是验签失败这么便宜——它是「发布端认为签的是 A、安装端认为验的是 B」。
2. **PG 与 MinIO 不一致时以 MinIO 为准，并报错而非自愈**。不一致意味着有人绕过了发布路径写库，这是安全事件，不是数据漂移。

## 3. 发布的原子性方向

发布是跨两个存储的写，不可能原子。方向必须选对：

```text
1. 上传字节到 MinIO（key = sha256(bytes)）   ← 幂等，可重放
2. 事务写 PG（artifacts + artifact_deps）    ← 有真相语义
```

**先字节后元数据**。反过来会在 PG 里留下「已发布但取不到字节」的记录——这个错误要到**安装期**才被发现，而安装期可能是几周后、在另一个集群、由不知情的人触发。顺序对了以后，失败残留是 MinIO 里的孤儿字节：内容寻址使它无害（同 digest 重传幂等），异步 GC 可后置到很久以后。

**判据不是「哪个更容易实现」，是「哪个方向的失败更便宜」。**

## 4. 不可变性与幂等

已发布的 `(name, version)` 不可覆盖：

- 重发**同 digest** → 幂等成功（重试、CI 重跑必须安全）
- 重发**不同 digest** → 拒绝，要求提版本号

这防的是最经典的供应链手法：不动版本号，悄悄换掉 `1.4.0` 的内容。已经装了 `1.4.0` 的节点不会重新拉取，新装的节点拿到的是另一份东西，而所有清单、所有审计日志上它们都叫 `1.4.0`。

## 5. 依赖闭包：冲突一律 fail closed

`resolve` 从根制品遍历 `deps` 求闭包，三种情况拒绝：

| 情况 | 处置 |
|---|---|
| 依赖成环 | 拒绝，报出环路径 |
| 同一制品在闭包内出现**多个版本** | **拒绝，不做自动仲裁** |
| 依赖的制品不存在 / 未发布 / 签名验不过 | 拒绝 |

第二条是判断题。包管理器通常自动选最高版本，但**制品带 scope 权限**：静默升版 = 静默提权。一个 `connector-jira@1.2` 声明 `scopes: [jira:read]`，`1.5` 改成了 `[jira:write]`，自动仲裁就把写权限装进了只申请读的部署里。口径与 `provenance`（未声明工具判 external）、`recovery`（孤儿意图转人工）一致：**不确定时把问题交给人，而不是替人做决定。**

## 6. 形态校验前移到安装计划期

manifest 的 `requires` 含形态声明（如 `{olap: true, graph: true}`）。目标部署形态不满足时，**在 `plan` 阶段拒绝并说明缺哪一项**（§13.2.3 已有此要求，本设计把它落到具体动作）。

不允许「装上去、运行时 seam 返回 `CapabilityUnavailable` 才失败」——那时失败点在一次真实业务调用里，报错面向的是终端用户而不是部署者。

**Nacos 偏离声明**：`ReleaseChannel`（灰度规则下发）本期以 PG `rollouts` 表实现，接口按 Nacos Config 的语义设计（订阅 + 热推）。与 Scheduler 选举用 PG 租约同因：Nacos 尚未进部署拓扑，先引入它会把本项的验证面从「注册表逻辑」扩大到「中间件接入」。**这是偏离规范 §6.1 的记账项，需与 N1 那条并列写进 `design-review.md` 落地状态，不得默默做掉。**

## 7. B1 判定树（写进 §4.3）

按**创作者与保证**分类，不按运行时引擎——运行时（Cordis 挂载 vs FlowEngine 执行）是实现细节，泄漏进产品分类会让开发者面对需求时无判定程序。

```text
这件东西改变了什么？
├─ 只塑造模型行为（prompt / 工具选择 / 策略）  → 技能 Skill
├─ 需要写新代码，提供带类型化 I/O 的服务契约   → 组件 Component
│   └─ 且该契约的另一端是外部系统              → 连接器 Connector
└─ 只连接既有件，不含新代码                    → 流程 Flow
```

智能体 Agent 不进这棵树：它是**引用的集合 + 角色定义**，是上述四类的消费者而非同层竞争者。

连接器独立成类由 §11.1 三入口决策定案（与产品结构一致），判定树保留它作为组件的子类，用途是**避免同类重复注册**——一个只调外部 API 的东西不应该既注册成组件又注册成连接器。

**边界自检**：一件制品若在「项目 / 能力资产 / 自动化」两个入口都能放，说明边界未划清。此检查随每次 schema 变更执行。

## 8. 验收判据

1. 五类 manifest schema 存在，非法 manifest 被 schema 拒绝且报出具体字段
2. 发布同 digest 幂等成功；同版本不同 digest 被拒
3. **篡改 PG 元数据不影响安装端执法**——测试直接改库里的 scope，安装计划仍按原始字节的 scope 生成（本设计的核心断言）
4. 篡改 MinIO 字节 → 验签失败 → 拒绝
5. 环 / 多版本 / 缺失依赖三种闭包错误各自被拒并报出路径
6. 形态不满足在 `plan` 阶段拒绝，不进入安装
7. publisher 授予超出自身上限的 scope 被拒
8. §4.3 判定树、§6.1 措辞修订、design-review T1/B1 落地状态三处文档同步

## 9. 已知不覆盖

- **publisher 私钥的保管与轮换**：本设计假定私钥在签名方手中且未泄漏。轮换机制（旧签名的宽限期、吊销列表）属密钥管理，随 Vault 接入做
- **制品运行时行为**：签名证明「字节没被改」和「谁发的」，**不证明它是良性的**。一个签名合法的组件照样可以是恶意的。这是签名机制的固有边界，靠 scope 上限与 §18 的来源分级限制爆炸半径，不靠签名
- **跨集群制品同步**：联邦场景下的 registry 复制未设计，随 N6 数据驻留一并处理
- **GC**：孤儿字节回收本期不做，只记录其无害性论证（§3）
